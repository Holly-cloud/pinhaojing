## 三、根因与修法

### 3.1 漂移根因

- **主根因**：`HANDOVER.md` 的「本地 git / 远端」两行在**写入时** HEAD 尚为旧值，其后又有新提交**未回填**。
  - 实证链：`12d5c53`（交接同步）写链时 HEAD = `e3e58ef`；其后 `00b4bfc`（根 README 分离）落地但未回填 → 两行各落后一格。
  - `PROJECT_MEMORY.md` 基线段更早：停留于 `b00e788`（v7.20 发布时点的快照），此后 **9 个提交**全未反映。
- **放大器**：**E10**（本机 ref 可能静默失败）使人不敢信任 `origin/master`，于是「远端到底同步到哪」长期靠**推测**而非实测 → 两文档对同一事实给出相反陈述（`HANDOVER:14` 说已同步、`HANDOVER:36` 说待推）。
- **性质**：**不是功能缺陷**，是交接资产的**事实性失真**——直接威胁 **C5 交接闭环判据③**。

## 附录 · 2026-09-21 追加：交付惯例入册（Holly 指令「第四条执行」）

**任务书**：用户指令「第四条执行」——指交付总结「建议后续」第 4 条：「凡有 commit/push 的交付，是否要求**同批**刷新 `HANDOVER` 的两行 + 抬头」。

**裁决**：立为**项目惯例**（**非铁律**）。依据 = 工程师建议「建议立为惯例（非铁律）」+ 主理人口径；且 `IRON_RULES.md` 的 P/E/C/T 区改动权归 Holly，agent 只能提议，故**未**由本次代劳升格为铁律。

**落点**：`dev/docs/ops/PROJECT_MEMORY.md` §交付惯例（接手第 2 步必读 · 活文件 · 知识唯一事实源），共 4 条：
1. 交付即同批同步交接状态（「更新 HANDOVER」须在**提交前**完成，使判据③在提交落地时即为真）
2. HEAD 必须写成**提交后仍成立**的形式（父提交 + 本提交性质 / 本文件最后修改所在提交；禁裸 hash 与「本轮最新」）
3. 数量类陈述先数物证再写（同源教训）
4. 判据③口径 = HEAD / 远端 / 版本 / 指纹 / 在途工作 / 待裁决项 六类字段与实测一致

**本轮按新惯例同批执行**（首次实践）：
- `HANDOVER.md`「本地 git」：裸 hash → 「本文件最后修改所在提交」+ 自校验命令 + 明示「HEAD 不在此冻结」；「远端」：未推送条数改为**以实测为准**，只冻结已推送的 `00b4bfc`
- `PROJECT_MEMORY.md`「当前基线」段同步改为稳健写法；抬头与「最近交付」记入本次入册
- **自校验实测**：`git log -1 --format='%h %s' -- HANDOVER.md` 与 `HEAD` **一致**（均指向「交付惯例入册」提交）→ 新写法**提交后仍然成立**；而旧写法「本轮提交其父 = `00b4bfc`」在**本批提交落地后即失效**，故予退役——这正是惯例 2 要堵的洞。

**验证**：本轮无产品变更（产物 324783 B / sha256 不变）；六类字段实测核对一致；`git status` 干净。
