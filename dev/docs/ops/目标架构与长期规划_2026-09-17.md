## 0. TL;DR（先给结论，再给证据）

**核心判断：PHJ 当前的架构不是"需要被推翻的债务"，而是一个"被误命名为小工具的高内聚引擎"。**
真正的架构风险**不在 `dev/src/`（那里相当健康）**，而在三条此前未被命名的断层线上：

| # | 断层 | 一句话 | 严重度 |
|---|---|---|---|
| **F1** | **发布形态的复制税** | 单文件 `file://` 交付是**产品红线**，但它把"源码结构"与"交付形态"锁死；一旦功能继续长，**单文件内联**会成为唯一的扩展上限 | ★★★ 战略级 |
| **F2** | **`shell/boot.js` 是隐藏的上帝对象** | 它不是"启动器"，是 **272 行 / 50 个事件监听器**的接线中枢；**14 个模块的真实耦合经由它** —— 审计数据里 `boot` 的被引用次数 **101，全项目第一** | ★★★ 结构级 |
| **F3** | **模块边界"写在注释里，没写在机制里"** | `PHJ.*` 是**显式导出面**，但**不是调用通道**；模块间仍共享同一 IIFE 作用域 → **边界可被静默绕过**（`boot.js` 直接调用别模块 101 次不经 `PHJ`） | ★★ 治理级 |

**推荐路线（两条腿，互不阻塞）：**

- **腿 A｜守住便携性红线，把"单文件"从"架构约束"降级为"打包产物"**：保持 `file://` 双击即用**对外不变**，但内部引入**产品皮肤层（skin）**，让"引擎"与"某一具体产品的文案/语料/默认值"解耦 → 这是从"一个小工具"长成"一个产品族"的唯一可行路径。
- **腿 B｜给边界装上机制**：把 F2/F3 从"注释约定"升级为"**闸门可证伪**"——`boot` 拆为 `shell/wiring/*`、`PHJ.*` 从"文档面"升为**唯一调用通道**（渐进式，不搞大爆炸）。

**一句话战略**：**PHJ 的下一个数量级，不是"加更多功能"，而是"让引擎与产品分离，让边界可被机器验证"。**

## 1. 现状体检：先纠正三个被误读的事实

在提方案前，必须先拆掉三处**认知偏差**——它们直接影响架构判断。

### 1.1 事实纠正

| 常见印象 | 审计实测 | 纠正 |
|---|---|---|
| 「`shell/boot.js` 是启动器，很轻」 | **272 行 / 14131 B / 50 个 `addEventListener` / 被引用 101 次（全项目第一）** | 它是**事件接线中枢 + 隐形上帝对象**，是当前最大的结构风险 |
| 「`shell/head.js` 是最大的文件之一（12468 B）」 | **43 行真实代码**，12468 B 中 **~12.4KB 是版本沿革注释** | 它只是**变更日志的宿主**，不是代码风险 |
| 「源码 185KB，注释适中」 | 全 JS 源码 185391 B，**块注释 50932 B = 27%**；其中 `head.js` 的单文件注释占全项目注释的 ~24% | **文档密度极高**是优点，但集中在 `head.js` 造成了"文件体积失真" |

> 方法论警告（值得写进项目惯例）：**`wc -l` 与 `bytes` 都不足以判断模块规模**。`head.js` 是 43 行却是第 6 大文件；`boot.js` 是"启动器"却承载了全项目 1/6 的监听器。**判断模块重量必须看「顶层声明数 + 监听器数 + 被引用数」三元组**，这正是本稿审计探针的取值口径。

### 1.2 真正健康的部分（不要动）

审计数据证明 `dev/src/` 的**内聚性相当好**：

- **无循环依赖**（跨模块依赖边 0 条环路）；
- **559 个顶层声明中，仅 225 个（40%）被跨模块引用 → 60% 是模块私有**；
- **108 个显式导出名中，只有 1 个（`textWidth`）是"导出但无人用"** → 导出面**几乎零冗余**；
- **会话态收编彻底**：16 个跨模块会话态变量**全部定义于 `core/store.js`**，P3 的目标已达成；
- **构建可复现**：`node dev/build.mjs` 实测产出 234243 B / sha256 `1abe0431…`，与 `BASELINE_v7.11.md` **逐字节一致**。

**结论：`dev/src/` 不需要"重构"。它需要的是"被机器验证的边界"和"产品层的解耦"。**

### 1.3 唯一的真技术债：重复导出行（新发现）

审计发现 **17 个模块中 16 个**存在**两条 `PHJ.<module> = {…}` 赋值**——P2 的全量导出行被紧随其后的 P3 收敛行**立即覆盖**：

```js
PHJ.store = { MIN_BLOCK_W, defaultState, drag, gridPos, … uid };                    // ← P2 行
PHJ.store = { MIN_BLOCK_W, …, keyDir, keyLastT, keyLoop, keyState, …, uid };        // ← P3 行（生效）
```

- **影响**：纯死代码，**运行期零影响**（后者整体覆盖前者）；
- **代价**：约 **3332 B 源码字节** + **16 处"读代码时的假信息源"**（读者会以为 P2 面仍生效）；
- **性质**：**"原地加标注而非删除"的档案惯例，被误用到了源码里**。档案惯例适用于 `dev/*.md`（保留史实），**不适用于可执行源码**（源码只保留生效态）。
- **处置建议**：删除 P2 行，并在文件头保留一行说明「P3 收敛后的对外面见下」。**这是唯一建议立即做的清理**。

## 2. 目标架构：分层 + 皮肤（Skin / Engine 分离）

### 2.1 设计原则（每条都对应一个已知断层）

| 原则 | 解决 | 说明 |
|---|---|---|
| **P1 交付形态 ≠ 源码结构** | F1 | 单文件是**打包结果**，不是设计约束。源码可以分层，产物仍单文件 |
| **P2 引擎零领域语义** | F1 | 引擎不含"古风甜宠/风格包"等领域内容；领域内容属**皮肤** |
| **P3 边界可被机器验证** | F2/F3 | 每条边界都要有**闸门断言**；注释不算边界 |
| **P4 单向依赖** | F2 | 箭头只向下：`shell → interact → view → editor → core`；`boot` 不得反向持有业务逻辑 |
| **P5 先可逆，后最优** | 全局 | 每步单独可回退；不追求一次性"最优架构" |

### 2.2 目标分层（在现有分层上补两处）

现有 **5 层物理分层已正确**（`shell/core/editor/view/interact`）——**不需要重新分层**。需要补的是**两处边界**：

```
┌──────────────────────────────────────────────────────────────────────┐
│  shell/            ── 外壳与启动                                      │
│    head.js             IIFE 首行 + 'use strict' + PHJ 骨架            │
│    wiring/  ★新        事件接线按「域」拆 5 片（取代 boot 的 50 监听） │
│        doc.js            DOMContentLoaded / resize / beforeunload      │
│        toolbar.js        顶栏（整理/缩放/导出/导入/补/导…）            │
│        spliceBar.js      拼接栏区（模板窗/预览/拼模式）                │
│        editorWin.js      编辑器窗 + 补全窗 + 片段库窗                   │
│        ctxMenu.js        右键菜单 + 通用 modal                        │
├──────────────────────────────────────────────────────────────────────┤
│  interact/         ── 输入路由（指针/键盘/粘贴）                        │
│  view/             ── DOM 生成（canvas/splice/overlay/modals）        │
│  editor/           ── 纯引擎（highlight/struct/complete/library）      │
│  core/             ── 状态与持久（store/persist/clipboard）            │
├──────────────────────────────────────────────────────────────────────┤
│  skin/  ★新        ── 产品皮肤（领域内容与产品文案的唯一边界）           │
│    corpus.js             内置语料：风格包 5 段 + 硬性要求 + 词表        │
│    copy.js               UI 文案（按钮名、toast、提示）                 │
│    defaults.js           默认状态（初始块文本、标题、分组顺序）          │
└──────────────────────────────────────────────────────────────────────┘
```

**硬规则：`core/` 与 `editor/` 不得 `require`/引用 `skin/`**——引擎只接受"注入的语料"，不知道自己服务于哪个产品。
这条规则让 `skin/` 成为**唯一**可以替换而不动引擎的边界 → 这是"产品族"的技术前提。

### 2.3 皮肤边界的现实价值（为什么这不是架构宇航）

**当下就有一个真实用例**：`complete.js` 里硬编码了 `CMPL_STYLE`（5 段风格包原文，约 1453 B）+ `CMPL_TAIL`。

- v7.8.2 已拍板「风格包即语料的一部分，放回内置」——**这个决定本身没问题**；
- 但审计显示：这段领域内容与「候选引擎的触发/评分/气泡/槽位逻辑」**住在同一个 521 行 / 126 顶层声明的文件里**，使 `complete.js` 成为**全项目最大模块**；
- 抽到 `skin/corpus.js` 后：`complete.js` 只留**机制**，语料可**独立版本化**（`CMPL_SEED_V` 的语义会从"内置表版本"变成"皮肤版本"，更准确）。

**收益**：`complete.js` 521 行 → 预计 ~380 行；且未来增加第二个语料主题（如"现代都市风"）**不需要碰引擎**。

### 2.4 关于 F1（单文件 vs 可扩展）的正面回答

**问题：单文件 `file://` 交付，会不会成为"大型系统"的天花板？**

**回答：会成为天花板，但不必现在打破它——正确做法是把天花板"推远"，而不是"取消"。**

| 方案 | 做法 | 评价 |
|---|---|---|
| ❌ 改成多文件 + `type=module` | 破坏 `file://` 双击红线 | **不可接受**（红线 3） |
| ❌ 引入打包器（rollup/esbuild） | 破坏「构建期零依赖」红线（红线 4） | **不可接受** |
| ✅ **维持单文件，把"产品族"建立在皮肤层** | 引擎 + 皮肤 → 同一套构建产出 N 个单文件 | **推荐** |
| ✅ 允许"可选外挂资产"（已有） | 导入/导出 JSON 已是既成事实（`cmpl.items`、写作资产） | **已是现成通道** |

**即：单文件不是限制，是"分发单元"。真正的扩展维度是「一套引擎 × N 套皮肤」，而这条路的**入口就是 §2.2 的 `skin/`**。

## 3. 迁移路线 R0–R4（承接 P0–P4，不重复其工作）

| 阶段 | 动作 | 是否改变产物字节 | 闸门期望 | 回退 |
|---|---|---|---|---|
| **R0 清债**（低风险，建议先做） | 删 16 处 P2 重复导出行；`textWidth` 从导出面移除（唯一零使用导出） | **变**（源码变 → 产物变）→ 需新基线 v7.12 | 7/7 全绿；断言**计数不变**（83/18/16/47/18） | git 单提交 |
| **R1 皮肤抽取**（解耦领域内容） | 新建 `skin/{corpus,copy,defaults}.js`；`complete.js` 的 `CMPL_STYLE/CMPL_TAIL/CMPL_GROUPS` 移入 `skin/corpus.js`；**引擎零领域语义**成为可断言的红线 | **变** → 需新基线 | 7/7；**新增 R1 断言**：`editor/**` 与 `core/**` 全文 0 命中 `skin/` 导入（证伪测试：故意加一行导入 → 必红） | git 单提交 |
| **R2 boot 拆分**（消解上帝对象） | `shell/boot.js` 的 50 个监听器按**域**拆入 `shell/wiring/*.js`（5 片）；**⚠️ 顺序敏感**（加载期注册序）→ 必须跑 P2-A 断言 | **变** → 需新基线 | 7/7；**P2-A 注册序契约必须绿**（这是本阶段最大风险点） | 逐片提交，可单片回退 |
| **R3 边界机制化**（把约定变断言） | ① `PHJ.*` 升为**唯一调用通道**（渐进：先新增 lint，不强制改造既有 101 处裸调用）；② 新增 R3 断言：跨模块调用的顶层名**必须出现在对方 `PHJ.<module>` 导出面**内 | **不变**（仅加校验，若 lint 为告警模式） | 7/7；R3 断言绿 | 纯加脚本 |
| **R4 产品族验证**（可选，验证 F1 判断） | 用 `skin/` 产出**第二套皮肤**（如"现代都市"语料）→ 同一引擎构建出第二个单文件，验证"引擎 × 皮肤"可行性 | 产物**新增**（不改 `PHJ.html`） | 两套产物闸门各 7/7 | 删除新皮肤 |

**关键排序理由**：
- **R0 先做**——它是**唯一**没有架构风险的清理，且能立刻消除 16 处假信息源；
- **R1 早于 R2**——R1 是"移动内容"（低风险），R2 是"重排事件注册序"（高风险）；先把低风险的解耦做完，R2 的风险面更小；
- **R3 不强制改造**——既有 101 处裸调用**继续工作**（同一 IIFE 作用域保证），lint 只对新代码生效，避免"数百处改动"的风险（沿用 `BASELINE_v7.11.md` 已拍板的"收益低、风险高 → 不做"判断）。

## 6. 结论

1. **`dev/src/` 不需要重构。** 它无循环依赖、60% 成员私有、导出面几乎零冗余、状态源已单一化——**这是一份健康的代码库**，P0–P4 的投入已兑现。
